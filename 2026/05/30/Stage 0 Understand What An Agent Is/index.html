Stage0 Understand What An Agent Is

2026-05-30
NLP>个人博客>学习笔记>留档>论文批判
1.9k 词
  • agent
区分 chatbot、workflow、agent、multi-agent。

chatbot只需要一个LLM+Prompt即可，核心模式是单轮或多轮对话，没有改变外部世界的能力。

而Agent需要严格的限定边界(沙箱机制)，产生可靠可审计的结果(结构化输出)，因此Agent需要架构设计。

按照学术界来讲Agent：拥有Perception，Planning，Memory，并能利用Tool对环境做出Action。

Workflow的步骤是定义好的；而agent的步骤是由其自己决定的。

如果你能提前画好项目的流程图，就用workflow；如果项目流程的改变依赖于输入，那就可能是Agent。

看一个最新的博客对于2026年Workflow和Agent的定义：

在Workflow中，LLM只有在特定情况下会被调用，并且顺序是固定的。

在Agent中，LLM是一个控制器，基于现在的任务决定调用什么工具，采取什么顺序。

multi-agent是由多个负责不同职责的agent协作完成任务的系统。

存在Agent之间的通信机制，可以并行执行任务。

可以通过角色分工和群体博弈，缓解单个LLM在处理复杂长链条任务上的上下文丢失和幻觉问题。

参考文献：

Agent workflow patterns for engineering teams

AI Agents vs Workflows: When to Use Each (With Examples) | Bananalabs

理解 agent 的基本循环：observe -> think -> act -> observe。

Agent的本质是一个感知，决策，行动的动态系统。

先观察环境，在进行思考对策(可能有CoT)，之后采取行动(Tool)，然后再观察Action之后的环境，如果think认为问题已经解决了，那么就执行结束的Action；否则继续执行Action改变环境。

参考文献：

[2210.03629] ReAct: Synergizing Reasoning and Acting in Language Models

明白什么时候不该用 agent：任务可预测、流程稳定、普通脚本能解决时，agent 反而增加不确定性。

如果你能提前画好项目的流程图，就用workflow；如果项目流程的改变依赖于输入，那就可能是Agent。

在项目流程确定的情况下不用Agent，即分支可以覆盖所有的情况，没有需要LLM判断下面执行步骤的情况。同时要求预算不高，响应时间迅速。

读完 Anthropic: Building effective agents。

保持Agent的简洁性：框架会简化标准底层任务，通常会创建额外的抽象层，从而掩盖底层的Prompt和Reponse，导致调试变得更加困难。

读完 OpenAI: A practical guide to building agents。

使用Agent时，应该先考虑将其用于难以自动化的工作流：

  • 复杂决策
  • 难以维护的规则系统
  • 强依赖非结构化数据

对于模型的选择，我们都知道应该对不同的任务选择不同的模型以降低成本，OpenAI给的策略是：

在构建Agent原型时，所有任务先统一使用最强模型，建立性能基线(baseline)。

在此基础上，再尝试替换为更小的模型，观察其是否能达到可接受的效果，这样可以避免过早限制Agent的能力。

Agent需要三类工具：Data，Action，Orchestration(Agent本身也可以作为工具被其他Agent调用)。

随着工具数量增加，应该把任务拆分成多个Agent。

Agent prompt的实践：

  • 使用已有文档。
  • 引导Agent拆解任务。
  • 明确动作定义。
  • 覆盖边界情况。

在单Agent的情况下，可以使用prompt templates管理复杂度。

与其为不同用例维护多个prompt，不如使用一个统一的基础的prompt，并通过变量进行配置。

何时考虑创建多个Agent：

复杂逻辑：当prompt包含大量条件语句，且prompt变得难以扩展时，可以将每个逻辑拆分到不同agent。

工具过载：问题不在于工具的数量，而在于工具的相似性和重叠性。如果已经使用了更清晰的工具名称，更明确的参数以及更详细的描述仍无法提升性能，则可以考虑使用多个Agent。

我的场景为什么需要 agent，而不是普通 workflow？

我的场景需要灵活性和由模型驱动的决策。

我的场景需要复杂的决策：涉及细粒度判断，异常情况处理和长上下文依赖；

我的场景由难以维护的规则系统：规则过于复杂且数量庞大，导致系统难以维护，更新成本高，容易出错。

我的场景强依赖非结构化数据：需要理解自然语言，从文档中提取信息或以对话方式和用户交互的场景。
