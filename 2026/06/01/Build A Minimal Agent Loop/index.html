Function calling | OpenAI API：

Function 和 Tool：Tool包含Function Tool和Custom Tool，Custom Tool不要求模型按照JSON Schema填写参数，而是让模型直接生成一段自由格式文本作为工具输入，因为有些场景很难用JSON Schema描述清楚，比如SQL生成、Shell命令，正则表达式和代码生成……

namespace：在定义Tool的时候，可以把一群工具打包成一个namespace，有助于组织功能相近的工具；命名空间可以帮助模型更准确地理解这些工具所属的业务领域。

延迟加载Deferred Loadding：可以在函数内部定义"defer_loading": true来实现延迟加载，只有模型判断确实该使用该工具时，才将其加载进来。

模型先看Namespace决定是否加载工具，Function Description帮助模型正确使用已经加载的工具。

定义函数的最佳实践：

  1. 编写清晰且详细的函数名、参数描述和使用说明：用System Prompt告诉什么时候用该函数，什么时候不用；包含示例(对于推理模型，大量增加示例可能会降低性能)和边界情况。
  2. 让函数设计简单直观：看到函数名称的人应该能大致猜出其的作用。
  3. 利用 Enum 和对象结构避免非法状态：尽量让错误状态在Schema层面无法表达。
  4. 通过”实习生测试”：如果把这个函数文档交给一个实习生，他能正确调用它吗？
  5. 尽量把负担从模型转移到代码：不要让模型填写你已经知道的信息；合并总是连续调用的函数。
  6. 保持初始可用函数数量较少

使用Fine-tuning可以降低Token消耗，通过Fine-tuning让模型学会你的工具体系，从而减少工具描述所需的Token数量。

在OPENAI的格式中，可以使用Tool Choice来进行附加配置。

tool_choice=”auto”：默认，允许模型调用任意个工具或者不调用工具。

tool_choice=”required”:要求模型至少调用一个工具。

tool_choice={“type”: “function”,”name”: “get_weather”}：要求模型只能调用指定函数

Allowed Tools：限制模型只能使用部分工具

使用Allowed Tools的主要原因是因为Prompt Cache，如果每次都修改tool，Prompt Cache很容易失效。会增加输入Token成本，并增加请求延迟。

Parallel Function Calling：普通的Function Tool支持并行调用，即模型可能在一次回复中同时调用多个工具。

Strict mode：官方建议使用开启Strict Mode，其可以保证函数调用严格遵守Schema。

开启StrictMode有两个条件：additionalProperties 必须为 false； properties 中所有字段必须出现在 required。

流式输出(Streaming):可用于展现模型的执行进度。

Custom Tools(自定义工具)：

Custom Tool和Function Tool的工作方式非常类似。

Function Tool Custom Tool
输入必须符合 JSON Schema 输入可以是任意文本
模型返回 JSON 参数 模型返回字符串
适合业务接口 适合代码、SQL、DSL 等

可以使用CFG（Context-Free Grammar）告诉模型生成的文本必须满足某种语法。。

Lark Grammar 或 Regex Grammar。

Function Tool 本质是：

自然语言
↓
JSON
↓
你的程序

Custom Tool + Grammar 变成：

自然语言
↓
受约束的目标语言
↓
你的程序

Custom Tool 特别适合代码执行器（code executor）、SQL 执行器和各种 DSL（领域专用语言）场景。

Gemini API Function Calling

在Gemini中，为了让模型在多轮 Tool Use 中保持推理连续性，需要把这个 Thinking Signature(内部思考的摘要)一起带回去。

Gemini支持并行函数调用和组合函数调用，组合函数调用即将多个函数调用链接在一起，以满足复杂的请求。

Gemini的api比openai封装的更抽象，Gemini的SDK相当于自己就是一个Agent了。
